Rekursionsbaum

Tastatur: Leertaste = Start/Pause, ← und → = einzelne Schritte

Beobachtungsauftrag

  1. Zähle die Ebenen des Baums für n = 8 und für n = 16. Wie viele Ebenen kommen dazu, wenn sich n verdoppelt?
  2. Sieh dir eine einzelne Ebene an: Wie viele Zahlen werden auf dieser Ebene insgesamt verschmolzen? Vergleiche das mit n.
  3. Drücke „↑ sortiert“ und dann „↓ umgekehrt“. Wie verändern sich die Vergleiche? Wie verändert sich die Anzahl der Schritte insgesamt? Was fällt dir auf?
  4. Suche einen Schritt, bei dem der Rest einer Teilliste ohne Vergleich angehängt wird. Wann passiert das?
  5. Mergesort braucht für das Verschmelzen Platz für eine zweite Liste. Erkläre, warum das bei Bubble Sort nicht nötig war.

Die Idee: Teile und herrsche

Mergesort besteht aus zwei Teilen, die getrennt betrachtet werden müssen:

Teilen kostet fast nichts. Die Liste wird in der Mitte durchgeschnitten – dazu muss nichts verglichen werden.
Verschmelzen kostet Arbeit. Zwei sortierte Listen der Gesamtlänge k zu einer sortierten Liste zu verbinden, braucht höchstens k − 1 Vergleiche, denn jeder Vergleich setzt genau eine Zahl endgültig.

Herleitung in zwei Schritten

1. Wie viele Ebenen hat der Baum? Jede Ebene halbiert die Länge der Teillisten: n → n/2 → n/4 → … → 1. Die Frage „Wie oft kann ich n halbieren, bis 1 übrig bleibt?“ ist genau die Definition des Logarithmus zur Basis 2.

Anzahl Ebenen = log₂(n)   →   n = 8 → 3 Ebenen  |  n = 1024 → 10 Ebenen

2. Was kostet eine Ebene? Auf jeder Ebene wird jede der n Zahlen genau einmal angefasst – egal, ob sie in vielen kleinen oder wenigen großen Verschmelzungen steckt. Eine Ebene kostet also rund n Operationen.

Gesamtaufwand ≈ (Kosten pro Ebene) × (Anzahl Ebenen) = n · log₂(n)

Best Case und Worst Case

Der entscheidende Punkt: Mergesort teilt immer exakt in der Mitte – unabhängig davon, welche Zahlen in der Liste stehen. Die Form des Baums hängt nur von n ab, nie von den Daten. Damit gibt es keine „ungünstige Eingabe“:

  • Worst Case: Bei jedem Verschmelzen wechseln sich beide Teillisten ab, jede Zahl kostet einen Vergleich → etwa n · log₂(n) Vergleiche.
  • Best Case: Eine Teilliste ist komplett kleiner als die andere, der Rest wird ohne Vergleich angehängt → etwa ½ · n · log₂(n) Vergleiche.
  • Beides unterscheidet sich nur um den Faktor 2. In beiden Fällen gilt O(n log n).
Vorsicht vor einem naheliegenden Irrtum: Die umgekehrt sortierte Liste ist bei Mergesort kein Worst Case, sondern ebenfalls ein Best Case – bei jedem Verschmelzen ist eine Teilliste komplett kleiner als die andere. Probiere es auf Seite 1 mit „↑ sortiert“ und „↓ umgekehrt“ aus: dieselbe Vergleichszahl. Der echte Worst Case ist eine verzahnte Folge, bei der beim Verschmelzen immer abwechselnd links und rechts zugegriffen wird (z. B. 1 5 3 7 2 6 4 8). Er muss regelrecht konstruiert werden – und kostet trotzdem nur den Faktor 2.
Merksatz: Mergesort ist zuverlässig. Es gibt keine Zahlenfolge, bei der das Verfahren plötzlich quadratisch wird. Genau darin unterscheidet es sich von Quicksort.

Gemessen: Vergleiche bei wachsendem n

Die Werte werden beim Öffnen dieser Seite tatsächlich berechnet, indem Mergesort auf Listen der jeweiligen Länge ausgeführt und jeder Vergleich mitgezählt wird.

Die letzte Spalte ist der Quotient Worst-Case-Vergleiche ÷ (n · log₂n). Dass er über alle Zeilen ungefähr gleich bleibt, ist der eigentliche Beleg dafür, dass n · log n die richtige Wachstumsordnung ist. Zum Vergleich: Bei n²/2 würde sich dieser Quotient mit jeder Zeile fast verdoppeln.

Mergesort gegen die einfachen Verfahren

Zum Vergleich: Bubble, Insertion und Selection Sort brauchen im Worst Case etwa n²/2 Vergleiche.

Python – einfache Variante mit Teillisten

Diese Umsetzung erzeugt bei jedem Aufruf neue Listen. Das ist etwas speicherhungriger als die Lehrbuchversion mit Indizes, dafür liest sie sich fast wie die Beschreibung des Verfahrens.

Zeile für Zeile

  • Zeile 2–3: Abbruchbedingung der Rekursion. Eine Liste mit 0 oder 1 Element ist bereits sortiert und wird unverändert zurückgegeben. Ohne diese Zeilen läuft das Programm endlos.
  • Zeile 5: // ist die Ganzzahldivision. Bei ungeradem n ist eine Hälfte um 1 länger – das stört nicht.
  • Zeile 6–7: liste[:mitte] ist die vordere Hälfte, liste[mitte:] die hintere. Beide werden durch den rekursiven Aufruf sortiert zurückgegeben.
  • Zeile 9: Erst jetzt wird verglichen – die ganze Arbeit steckt in verschmelze.

Die Hilfsfunktion verschmelze

  • Zeile 2–4: ergebnis ist die neue Liste, i und j zeigen jeweils auf das vorderste noch nicht benutzte Element.
  • Zeile 6: Die Schleife läuft nur so lange, wie in beiden Listen noch etwas steht.
  • Zeile 7–12: Die kleinere der beiden vordersten Zahlen wird angehängt, der zugehörige Zeiger rückt eins weiter.
  • Zeile 15–20: Eine Liste ist leer – der Rest der anderen wird angehängt. Hier wird nicht mehr verglichen, das ist die Erklärung für den Best Case.
  • <= statt < in Zeile 7 sorgt dafür, dass gleiche Werte ihre ursprüngliche Reihenfolge behalten (Mergesort ist stabil).

Aufrufprotokoll für deine aktuelle Zahlenfolge

Einrückung = Rekursionstiefe. Beachte die Reihenfolge: Erst wird bis ganz nach unten aufgerufen, danach wird von unten nach oben verschmolzen.
