Was kostet ein Zerlegungsschritt?

Beim Zerlegen (Partitionieren) wird jedes Element der Teilliste genau einmal mit dem Pivot verglichen. Eine Teilliste der Länge k kostet also k − 1 Vergleiche – unabhängig davon, wie gut oder schlecht das Pivot ist.

Der Unterschied zwischen schnell und langsam steckt also nicht im einzelnen Zerlegungsschritt, sondern darin, wie viele Ebenen der Rekursionsbaum bekommt. Und das entscheidet allein die Pivotwahl.

Best Case – Pivot trifft die Mitte

Beide Teillisten sind etwa gleich lang: n/2 und n/2. Die Länge halbiert sich pro Ebene, es gibt also log₂(n) Ebenen. Auf jeder Ebene werden zusammen höchstens n Elemente verglichen.

C(n) = 2 · C(n/2) + (n−1)   →   C(n) ≈ n · log₂(n)

n = 1024 → rund 10 000 Vergleiche.

Worst Case – Pivot ist das kleinste oder größte Element

Eine Teilliste ist leer, die andere hat n−1 Elemente. Es wird nur ein einziges Element pro Ebene festgesetzt, der Baum wird zu einer langen Kette der Tiefe n−1.

C(n) = C(n−1) + (n−1)   →   C(n) = n·(n−1)/2 ≈ n²/2

n = 1024 → rund 524 000 Vergleiche – gut 50-mal so viel.

Der gefährliche Standardfall

Nimmt man immer das letzte (oder immer das erste) Element als Pivot, dann tritt der Worst Case ausgerechnet bei einer bereits sortierten Liste ein: Das letzte Element ist dann immer das Größte, die rechte Teilliste bleibt jedes Mal leer. Sortierte oder fast sortierte Daten sind in der Praxis aber keine Seltenheit, sondern der Normalfall – genau deshalb ist diese Pivotwahl gefährlich.

Nimmt man das mittlere Element, ist derselbe Fall der beste überhaupt: Das mittlere Element einer sortierten Liste ist genau der Median, die Teillisten werden exakt gleich lang.

Wichtig für das Verständnis: Auch die Wahl „mittleres Element“ hat einen Worst Case – man kann eine Eingabe konstruieren, die genau diese Wahl aushängt. Es gibt keine feste Pivotregel ohne Worst Case. Deshalb wählen praktische Implementierungen das Pivot zufällig oder als Median aus drei Werten: Der Worst Case verschwindet dadurch nicht, aber er hängt nicht mehr von der Eingabe ab und wird extrem unwahrscheinlich.

Vergleich mit Mergesort

Mergesort teilt immer exakt in der Mitte, weil es nach Positionen teilt und nicht nach Werten. Deshalb hat es keinen quadratischen Fall – dafür braucht es zusätzlichen Speicher. Quicksort arbeitet ohne Zusatzspeicher direkt in der Liste und ist in der Praxis meist schneller, riskiert dafür den Worst Case.

Python – einfache Variante mit Teillisten

Diese Fassung baut bei jedem Aufruf neue Listen. Sie ist nicht die speichersparendste, aber sie zeigt die Idee von Quicksort in wenigen Zeilen und ohne Index-Jonglage.

Zeile für Zeile

  • Zeile 2–3: Abbruch der Rekursion: 0 oder 1 Element ist immer sortiert.
  • Zeile 5: Das Pivot wird festgelegt – hier das erste Element. Diese eine Zeile entscheidet über die Laufzeit.
  • Zeile 6: liste[1:] ist der Rest ohne das Pivot. Wichtig: Das Pivot darf nicht noch einmal einsortiert werden.
  • Zeile 8–14: Jedes Element des Rests wird einmal mit dem Pivot verglichen und in einen der beiden Eimer gelegt. Das sind die k−1 Vergleiche.
  • Zeile 16: Beide Eimer werden rekursiv sortiert und mit dem Pivot dazwischen zusammengehängt. Das Pivot steht bereits endgültig richtig.

Dieselbe Funktion mit besserem Pivot

Nur der Anfang ändert sich – und aus dem Worst Case bei sortierten Daten wird der Best Case:

  • Zeile 5–6: len(liste) // 2 ist die Position der Mitte, liste[m] der Wert dort.
  • Zeile 7: Der Rest wird aus dem Stück vor und dem Stück nach dem Pivot zusammengesetzt. Der Pivot-Platz m wird dabei übersprungen.
  • Der übrige Code bleibt Zeile für Zeile identisch.
  • Kurzschreibweise für die beiden Eimer (später, wenn Listenkomprehension bekannt ist):
    kleiner = [x for x in rest if x <= pivot]
Diese Variante ist nicht in place: Sie legt neue Listen an und braucht deshalb zusätzlichen Speicher. Die Lehrbuchversion sortiert mit zwei Indizes direkt in der Liste – die Animation auf Seite 1 zeigt genau diese Version. Die Anzahl der Vergleiche ist bei beiden gleich.
